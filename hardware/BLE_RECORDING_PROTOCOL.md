# NU40 ↔ Arduino UNO Q 녹음 BLE 규약 v1

## 역할

NU40: IMU 흔들기 감지 → 녹음 시작 요청.
UNO Q: 요청 수신 → 아이폰에 녹음 요청 → 파일 수신 → 결과 전달.
아이폰: 내장/헤드셋 마이크로 녹음하고 네트워크로 UNO Q에 파일 전송.
BLE는 요청/결과만 전달한다. 음성 전송, 아이폰 앱, 음성인식은 이 펌웨어에 구현하지 않았다.

## 연결과 바이트

NU40는 Peripheral, UNO Q는 Central이다. 개발 시 PC로 UNO Q를 대신할 수 있다.
광고 이름은 `NU40-BLE-Test`. 한 Central만 연결하므로 PC와 UNO Q를 동시에 연결하지 않는다.

| 항목 | UUID |
| --- | --- |
| Nordic UART 서비스 | `6e400001-b5a3-f393-e0a9-e50e24dcca9e` |
| RX (UNO Q → NU40, Write) | `6e400002-b5a3-f393-e0a9-e50e24dcca9e` |
| TX (NU40 → UNO Q, Notify) | `6e400003-b5a3-f393-e0a9-e50e24dcca9e` |

UNO Q는 연결 후 서비스 확인 및 TX 알림 구독(CCCD 활성화)을 먼저 한다.
UNO Q Python에는 BlueZ/D-Bus 접근이 필요하다. App Lab 컨테이너 접근 설정은 별도 확인한다.
MAC 주소 고정값에 의존하지 않는다.

| 문자 | Hex | 방향 | 의미 |
| --- | --- | --- | --- |
| `s` | `0x73` | NU40 → UNO Q | 녹음 시작 **요청** |
| `c` | `0x63` | UNO Q → NU40 | 아이폰 녹음 완료 + UNO Q의 정상 파일 수신 확인 |
| `r` | `0x72` | UNO Q → NU40 | 녹음 실패/음성 부족 등으로 재녹음 필요 |

메시지는 ASCII 1바이트다: `b's'`, `b'c'`, `b'r'`. 개행/JSON/ACK/진단 문자열을 섞지 않는다.
Notify를 바이트 단위로 해석한다. 알 수 없는 수신 바이트는 NU40가 무시한다.
기존 BLE `s=상태조회`, `r=반복진동` 명령은 폐기했다. 진단은 USB Serial 전용이다.
`s`는 실제 녹음 시작 확인이 아니다. v1에는 녹음 시작 ACK가 없다.
GATT Write 응답도 물리적 진동/파일 수신 성공을 보장하지 않는다.

## 상태와 예외

1. `IDLE`: 흔들면 연결/구독 확인 후 `s`를 한 번 보내고 `WAITING_RESULT`.
2. `WAITING_RESULT`: 추가 흔들기를 무시. UNO Q는 아이폰에 녹음을 요청하고 결과를 기다린다.
3. `c`: `IDLE`로 복귀하고 짧은 진동 2회 (120ms ON / 160ms 사이 간격).
4. `r`: `RETRY_REQUIRED`로 전환하고 짧고 빠른 진동 4회 (60ms ON / 60ms 사이 간격). **자동 녹음하지 않고 다음 흔들기를 기다린다.** 다시 흔들면 새 `s`.
5. 60초 동안 결과 없음: `RETRY_REQUIRED`. 자동 재전송 없이 새 흔들기를 기다린다.
6. 연결 또는 TX 알림 구독 해제: NU40 요청 취소 및 `IDLE`. 재연결/구독 후 새 흔들기부터 시작한다.

대기 중이 아닐 때의 `c`/`r`은 무시한다. UNO Q도 중복 `s`로 녹음을 두 번 시작하지 않는다.
UNO Q는 요청당 `c` 또는 `r` 하나만 보내고, 연결 해제 시 아이폰 요청도 취소한다.
v1은 요청 ID가 없어 늦은 이전 결과를 새 결과와 구분할 수 없다.
UNO Q는 자체 타임아웃을 60초보다 짧게 두고 실패 시 `r`을 보낸 후 이전 결과를 버린다.
재연결 후 이전 세션 결과를 보내지 않는다. 더 높은 신뢰성이 필요하면 차기 버전에 ID/시작 ACK를 추가한다.

## 흔들기

IMU는 20ms마다 읽고 USB/3D는 100ms마다 표시한다.
현재 실측 센서는 주소 `0x6A`, WHO_AM_I=`0x6A`인 LSM6 계열이다.
저역통과 추정으로 중력 성분을 제거하고 동적 가속도 0.65g 이상의 반대 방향 피크 3개를 700ms 안에 요구한다.
피크 간 최소 80ms, 트리거/결과 후 1.5초 억제, 모터 작동 중 및 진동 시작 후 1초 억제.
기본 반복 진동은 껐다. `c`는 2회, `r`은 빠른 4회로 구분한다.
4개 LED는 기본적으로 꺼져 있으며, 실제 보드의 active-LOW PWM으로 밝기를 제어한다.
BLE 라이브러리의 자동 연결 LED는 비활성화한다.

| 상태 | LED 애니메이션 | 진동 |
| --- | --- | --- |
| 대기 | 모두 꺼짐 | 없음 |
| `s` 전송 후 결과 대기 | 잔상이 있는 점이 좌우 왕복. 편도 200ms 이동 후 끝에서 400ms 정지 | 없음 |
| `c` 완료 | 4개가 함께 900ms 동안 부드럽게 밝아졌다 어두워지고 모두 꺼짐 | 짧게 2회 |
| `r` 재시도 필요 | 편도 140ms 이동 + 60ms 정지로 1.6초 동안 빠르게 왕복, 이후 양 끝 LED가 약하게 호흡 | 빠르게 4회 |

새 `s`는 재시도 표시를 녹음 대기 애니메이션으로 바꾼다. 연결 해제/구독 해제 시 모두 끈다.
LED 프레임은 5ms, IMU는 20ms, 진동은 각각 독립적인 millis 일정으로 처리하며 delay를 사용하지 않는다.
`LedFeedback.h`에 패턴과 밝기 처리를 모았다. USB `d`의 LED feedback 값은 0=꺼짐, 1=녹음 대기, 2=완료, 3=재시도다.
3D 창은 USB의 `RECORD TX s` 이벤트를 받아 배경을 노란색으로 바꾼다.
이 이벤트는 NU40가 BLE Notify 전송을 큐에 넣은 뒤 출력한다. 실제 상대 수신은 BLE 콘솔의 `s`로 확인한다.
`c`/`r` 수신 또는 연결 해제/타임아웃 후 3D 배경은 기본색으로 돌아간다.
임계값은 초기값이며 실제 착용/걷기/달리기에서 오감지를 확인하고 조정해야 한다.

## UNO Q 담당 AI의 작업

- `hardware/ble_recording_peer.py`는 Bleak 수신/송신 참고 코드이자 **수동 테스트 도구**다. 실제 녹음하지 않는다.
- `s` 콜백에서는 요청을 비동기 큐에 넣고, 한 번에 아이폰 녹음 세션 하나만 실행한다.
- 아이폰에 네트워크로 녹음 시작 요청, 파일 수신 및 검증 후 `write_gatt_char(RX, b'c', response=True)`.
- 아이폰 미연결/녹음 실패/음성 부족/자체 타임아웃이면 `write_gatt_char(RX, b'r', response=True)`.
- `r` 후 새 `s`를 기다린다. 파일 수신 후 음성인식/LLM 처리를 이어간다.
- 아이폰 앱, 네트워크 프로토콜, 인증/권한, 녹음 종료 조건은 별도 구현한다.

## 테스트와 파일

펌웨어: `hardware/NU40_Basic_Test/NU40_Basic_Test.ino`, `RecordingProtocol.h`, `ImuTest.h`.
PC: `hardware/ble_test.cmd`. UNO Q: Bleak 설치 후 `python3 hardware/ble_recording_peer.py`.
흔들기 → `s` 확인 → 콘솔에서 `c`/`r` 입력. 대기 중 추가 흔들기는 무시되고 `r` 후 새 흔들기에서 새 `s`가 나와야 한다.
`hardware/ble_connection_test.py`도 새 규약 테스트로 연결되는 호환 진입점이다. 이전 PONG 테스트는 폐기했다.

USB Serial 115200bps 전용 명령:

| 문자 | 동작 |
| --- | --- |
| `g` | 흔들기와 같은 녹음 요청을 수동 발생; 연결/구독 필수 |
| `d` | 녹음 상태 및 모터/LED/BLE 진단 |
| `i` / `o` | 100ms IMU 출력 시작 / 중지 |
| `v` / `h` / `x` | 진동 2회 / 반복 진동 / 정지 |

`g`는 연동 검증용이며 실제 흔들기 판정을 검증하지 않는다.
이 문서 밖의 BLE 문자를 임의로 추가하지 않는다.

## 검증 범위 (2026-10-10)

NU40에 컴파일/자동 USB 업로드 완료. PC를 UNO Q의 Central 대역으로 사용해 실제 BLE에서 검증했다.
연결/구독 없이 시작 차단, 정확한 `b's'` 알림, 대기 중 중복 요청 차단,
`r` → 재필요 → 새 요청, `c` → IDLE, 이전/알 수 없는 결과 무시,
구독 해제 시 요청 취소, 재연결/재구독 후 새 요청 및 100ms IMU 출력을 확인했다.
첫 연동 검증은 USB `g`로 요청을 발생시켰다. 이후 실제 흔들기 검증은 아래에 기록한다.
걷기/달리기에서의 오감지, 60초 타임아웃, UNO Q의 Linux 연결 및 아이폰 실제 녹음/파일 전송은 아직 검증하지 않았다.

### 구분된 진동 피드백 검증

실제 PC ↔ NU40 BLE로 `c`/`r`을 송신했다. USB 드라이버 로그에서
`c`: 2개 펄스, 종료 간격 281ms; `r`: 4개 펄스, 종료 간격 122ms를 확인했다.
두 경우 DA7280 오류는 `0x00`, LED 최대 프레임 간격은 6ms였다.
이 값은 전기적 구동 명령/드라이버 상태 검증이며 실제 체감은 사용자가 확인해야 한다.
수동 `g`를 통한 연동 검증과 실제 IMU 흔들기 검증을 혼동하지 않는다.

실제 사용자 흔들기에서도 USB `RECORD TX s`와 PC BLE 콘솔의 `NU40 -> s`를 함께 확인했다.
이어 사용자가 콘솔에서 보낸 `r`이 보드에 도착하고 4개 펄스가 실행됐다.
다시 실제로 흔든 뒤 사용자가 보낸 `c`도 보드에 도착하고 2개 펄스가 실행됐다.
3D 창의 실제 노란 배경과 `SHAKE DETECTED / BLE s SENT` 표시도 화면에서 확인했다.
현재 실측 상대는 PC 테스트 Central이며 UNO Q의 Linux 수신 프로그램을 실행한 결과는 아니다.

새 LED 피드백 펌웨어에서도 실제 PC BLE c/r 및 진동 2회/4회를 확인했다. c 후 LED 상태 0, r 후 상태 3을 확인했다. 해당 실행의 최대 LED 프레임 간격은 각각 16ms/5ms였다. LED의 실제 육안 표현은 사용자 확인이 필요하다.
